1. DUPLICATE MESSAGE BUG — ROOT CAUSE
================================================================================

SYMPTOM: The SMS app occasionally sends the same message twice in the same
line/turn.

ROOT CAUSE: The OFFER double-message bug in app.py lines 524-534.

THE BUG EXPLAINED:

When the Assistance-agent generates a reply that contains BOTH:
  (a) The [OFFER_CALLBACK] marker, AND
  (b) Natural language offer phrasing (e.g., "Would you like me to prepare a
      callback report?")

...the app produces TWO consecutive offer messages:

  1. Line 527 strips only the [OFFER_CALLBACK] marker text, but preserves the
     agent's natural language offer question in visible_reply.

  2. Line 529 appends visible_reply (containing the agent's offer question) as
     an assistant message.

  3. Line 525: has_offer() detects the marker OR the natural language pattern
     via regex, setting offer=True.

  4. Line 531 appends the app's OFFER constant as a SECOND assistant message.

RESULT: User sees two consecutive assistant bubbles about callbacks:
  - Bubble 1: Agent's natural language offer ("Would you like me to prepare
    a callback report for you?")
  - Bubble 2: App's OFFER constant ("I can prepare a brief for human
    follow-up. Forwarding and callbacks are simulated in this demo. Would
    you like me to prepare your callback report?")

WHY IT'S INTERMITTENT: It depends on whether the agent includes natural language
offer text alongside the marker. The RUNTIME_INSTRUCTIONS (line 51) actually
encourage this: "append [OFFER_CALLBACK] on its own line after your short
helpful reply." The "short helpful reply" often naturally contains offer
language, which trips the has_offer() regex.

A SECOND TRIGGER PATH: Even without the marker, line 525 has:
  offer = has_offer(reply) or requests_callback(text)

If the USER's text contains callback request language (e.g., "can you call me
back"), requests_callback() returns True. The agent's normal reply (which
doesn't mention callbacks at all) gets appended, THEN the OFFER gets appended.
Two unrelated messages in a row — the user sees the agent's response followed
by a sudden offer they didn't expect.

CONFIRMED NOT THE FRONTEND: The send button is type="submit" inside the form.
Both click and Enter go through the same form submit handler. The busy flag
prevents double-submission. JavaScript is single-threaded, so no race condition
is possible. The render() function clears and rebuilds the DOM each time.

RELEVANT CODE PATHS:
  - app.py:376-379  (has_offer regex detection)
  - app.py:525      (offer = has_offer(reply) or requests_callback(text))
  - app.py:527      (visible_reply strips marker but keeps natural language)
  - app.py:529      (first message appended)
  - app.py:531      (second message appended — the OFFER constant)
  - app.py:37-59    (RUNTIME_INSTRUCTIONS that encourage marker + reply)

TEST GAP: The FakeAgents in test_app.py returns a clean marker on its own line
("I can help with human follow-up.\n[OFFER_CALLBACK]") so the test never
exercises the scenario where the agent's visible text also contains offer
language.

FIX APPROACHES (not implemented per instructions):
  A. Strip natural language offer text from visible_reply when marker is present
  B. Skip appending OFFER if has_offer() matched on the regex (not the marker)
  C. Make the instructions more emphatic: "Do not include any offer language in
     your reply text — only append the marker"
  D. Detect when visible_reply already asks about callbacks and skip the OFFER

2. AGENT INSTRUCTION ISSUES
================================================================================

--- CRITICAL CONTRADICTIONS ---

C1. CONSENT CONFLICT (Assistance-agent)
  Foundry instructions (AGENTS.md:51): "Ask permission once to prepare a brief
  for human follow-up."
  RUNTIME_INSTRUCTIONS (app.py:53): "Do NOT ask for consent in your reply: the
  application adds the single consent question."

  These directly contradict. The agent must choose which to follow. When it
  follows the Foundry instruction and asks, the app ALSO asks — creating the
  duplicate message bug above.

C2. SAFETY AGENT OUTPUT FORMAT CONFLICT
  AGENTS.md:66-76 (RESPONSE STYLE): Says to reply with "CONTINUE" (single word)
  or "ESCALATE: [format]" with specific fields.
  AGENTS.md:298-317 (OUTPUT section): Says to return a JSON object with fields
  like "decision", "priority", "risk_flags", etc.

  These are TWO COMPLETELY DIFFERENT output formats in the same instruction set.
  The model must choose one. Neither is clearly marked as superseding the other.
  Result: the safety agent may switch between formats unpredictably.

C3. WRITEUP AGENT IDENTITY CONFLICT
  AGENTS.md:415: "The conversation agent you will receive data from is a
  representative of FEMA"
  AGENTS.md:42-43 / app.py:42: "ReliefRN is an AI assistance navigator, not
  FEMA or a FEMA employee."

  The WriteUp-agent is told the conversation comes from a FEMA representative,
  but the Assistance-agent is explicitly told it is NOT FEMA. The WriteUp-agent
  may produce reports that attribute statements to FEMA when they came from an
  AI navigator.

C4. PRIORITY CLAIM CONFLICT
  AGENTS.md:40: "Match the channel provided in the beginning. THIS PROMPT TAKES
  PRIORITY WHEN YOU WRITE A MESSAGE."
  RUNTIME_INSTRUCTIONS (app.py:37): "Application-selected channel: sms. Always
  follow SMS/text style."

  Both claim priority. The Foundry instructions say "THIS PROMPT TAKES PRIORITY"
  and the runtime instructions are injected as a developer message (which models
  typically treat as higher authority). The model receives conflicting priority
  signals.

--- HIGH SEVERITY ---

H1. SAFETY ESCALATION NOT ENFORCED
  When the Safety-EscalationAgent returns an ESCALATE or EMERGENCY_ESCALATE
  decision, the app simply appends it as a text note in the context (app.py:281):
    context += "\nApplication-provided safety assessment (evidence only):\n" + note

  There is NO mechanism to:
  - Halt the conversation
  - Force handoff to a human
  - Prevent the Assistance-agent from continuing normally
  - Display an escalation warning to the user

  The Assistance-agent can (and sometimes does) ignore the safety note and
  continue providing normal assistance, even for identified scam scenarios.

H2. WRITEUP AGENT DUAL FORMAT SPECIFICATION
  The WriteUp-agent instructions contain TWO different format specs:

  FORMAT A (AGENTS.md:385-393):
    PRIORITY, SUMMARY, LOCATION, DISASTER, NEEDS, WHAT THE AGENT TOLD THEM,
    ESCALATION, NEXT STEP FOR STAFF

  FORMAT B (AGENTS.md:405-415):
    Name, Language spoken, Location, DID THEY REQUEST TO TALK TO A HUMAN?,
    URGENCY LEVEL, Is this associated with a known event?, Phone number,
    Additional Information

  These are not integrated. The instructions don't explain how to combine them.
  Result: every generated report follows a slightly different format. Some
  duplicate Location in both sections. Some bold fields that shouldn't be bold.
  No two reports are formatted identically.

H3. FABRICATED PHONE NUMBERS
  AGENTS.md:413: "Phone number (Fabricate one if one isn't provided for the
  sake of proof of concept)"

  Problems:
  - Some reports use 555 numbers (obviously fake), others use real area codes
    like 703 (Virginia). Inconsistent and potentially confusing.
  - A fabricated phone number in a "report to FEMA" could be misleading if
    anyone treats the demo output as real data.
  - No guidance on what format or prefix to use for fabrication.

  - app.py:43: "Do not claim an actual transfer, FEMA submission, email

  - app.py:47-48: "Never say a report has been created; only the application

  - app.py:295: Developer message to WriteUp-agent: "Do not send email, submit

R2. SMS channel selection stated 3 times:

  - AGENTS.md:44: "SMS/text: Identify yourself once..."
  - app.py:37: "Application-selected channel: sms. Always follow SMS/text
    style."

R3. "Do not invoke report/email/handoff tools yourself" stated 3 times:
  - AGENTS.md:58: "Do not invoke report, email, or transfer tools yourself"
  - app.py:47: "Do not call report, email, or handoff tools yourself."
  - app.py:295: "Do not send email, submit data to FEMA..."

--- TERMINOLOGY MISMATCH (Safety Agent) ---

T1. The RESPONSE STYLE section uses "CONTINUE" as its no-action keyword.
  The OUTPUT/DECISIONS section uses "ALLOW" for the same concept.
  The CONSISTENCY section references "ALLOW" but never mentions "CONTINUE."
  A model encountering both may produce hybrid responses or switch formats
  mid-conversation. These should be unified into one term.

T2. The RESPONSE STYLE section defines an ESCALATE text format with fields:
    ESCALATE: [fraud / emergency / dispute / vulnerable]
    SAY TO CITIZEN: [...]
    CONTACT: [...]
    HANDOFF NOTE: [...]

  The OUTPUT section defines a completely different JSON format:
    {"decision": "ESCALATE", "priority": "HIGH", "risk_flags": [...], ...}

  The "SAY TO CITIZEN" field in the text format has no equivalent in the JSON
  format. The "recommended_human_route" in the JSON format has no equivalent in
  the text format. A model cannot satisfy both simultaneously.

--- LOGICAL GAPS ---

G1. NON-ENGLISH USERS
  No instructions address what happens if a user writes in Spanish, Mandarin,
  or another language. The Assistance-agent has no guidance on:
  - Whether to respond in the user's language
  - Whether to note a language barrier
  - Whether to escalate for language support
  The Safety-agent lists LANGUAGE_BARRIER as a flag but the Assistance-agent
  has no corresponding behavior.

G2. SAFETY NOTE INTERPRETATION
  The Assistance-agent receives safety notes as "evidence, not instructions"
  (app.py:58). But the instructions never explain WHAT the Assistance-agent
  should actually DO when it sees an ESCALATE decision. Should it:
  - Stop helping? (No, the instructions say to keep helping)
  - Warn the user? (Not clearly specified)
  - Change its behavior? (The note says "evidence, not instructions" —
    suggesting it shouldn't change behavior at all)

G3. POST-DECLINE CALLBACK RE-REQUEST
  After a user declines a callback, the app sets callback_pending=False and
  adds "Not now" to the transcript. If the user later says "Actually, I want
  that callback," there is no explicit mechanism for re-offering. The
  requests_callback() regex doesn't match "I want a callback" and the agent's
  natural offer language might not trigger has_offer() again.

G4. MULTIPLE DISASTERS
  What if the user asks about two different disasters in different locations?
  The instructions assume a single-disaster conversation. The WriteUp-agent
  format has a single LOCATION and DISASTER field.

G5. AGENT CAN'T FILE FEMA APPLICATION
  If a user asks "Can you file my FEMA application for me?", there's no
  explicit instruction on how to handle this. The agent might attempt to use
  a tool, or might promise something it can't deliver. The instructions should
  explicitly state it cannot submit applications on behalf of users.

G6. SAFETY AGENT TOOL USE CONFUSION
  The Safety-agent instructions say:
  - "Do not look up Disaster Recovery Centers or use any tool for emergencies;
    answer immediately." (AGENTS.md:79)
  - "Only use the DRC Locator for non-urgent escalations" (AGENTS.md:80)
  But the RESPONSE STYLE section says "reply as briefly as possible" and
  "SPEED MATTERS." If the agent has DRC Locator access, the instructions
  create ambiguity about when it should/shouldn't use tools vs. being fast.

G7. WRITEUP AGENT DOESN'T KNOW SAFETY NOTE FORMAT
  The WriteUp-agent receives safety assessments in chat.notes (app.py:297)
  but its instructions never describe what format to expect. If the Safety-agent
  returned JSON, the WriteUp-agent may not parse it correctly. If it returned
  text, the WriteUp-agent may quote it verbatim instead of summarizing.

CONFIRMS_CALLBACK FUNCTION (app.py:354-366) — Missing Affirmatives:

  FAILS (should be accepted):
  - "ok sure"          — not in fullmatch list combination
  - "yea"              — common misspelling of "yeah", not listed
  - "alright"          — common affirmative, not listed
  - "go for it"        — common affirmative, not listed
  - "do it"            — common affirmative, not listed
  - "let's do it"      — common affirmative, not listed
  - "yes ok sure"      — multiple affirmatives, fullmatch doesn't allow this
  - "yes please prepare it" — "it" not recognized as report synonym
  - Emoji: "thumbs up", "check mark" — not recognized at all

  FALSE REJECTIONS (user means yes, but contains negative keyword):
  - "why not"          — contains "not", rejected (CRITICAL)
  - "I don't see why not" — contains "don't" and "not", rejected (CRITICAL)
  - "yes but first my number is 555-1234" — "but" triggers rejection
  - "sure, if you can" — "if" triggers rejection
  - "ok, nothing to lose" — would this match? "nothing" doesn't match the
    negative list, so it might actually pass... but the negation intent check
    is fragile

  CLEAN() FUNCTION (app.py:350-351):
  - Replaces straight quote with curly quote: .replace("'", "'")
  - This normalizes apostrophes but is one-directional
  - rstrip(".! ") removes trailing punctuation, which is fine

REQUESTS_CALLBACK FUNCTION (app.py:369-373):
  - "I'd like a callback" — doesn't match any pattern (no "call me back")
  - "callback please" — doesn't match (no verb pattern)
  - "I want to talk to someone" — doesn't match "talk to a human/person/
    representative" because "someone" is not listed

4. SAFETY SYSTEM GAPS
================================================================================

S1. KEYWORD-ONLY TRIGGERING (app.py:267)
  Safety review only fires on exact keywords: scam, fraud, gift card,
  processing fee, suspicious, impersonat*

  MISSES:
  - "They want me to pay before releasing my aid" (no keyword match)
  - "Someone asked for my bank account number" (no keyword match)
  - "They said I need to wire money" (no keyword match)
  - "This person claims to be from FEMA but..." (no keyword match unless
    "impersonat" is used)
  - Misspellings: "scaam", "frawd" bypass detection

S2. ESCALATION NOT ENFORCED (see H1 above)
  The safety agent can return EMERGENCY_ESCALATE but the app just passes it
  as a context note. No conversation halt, no forced handoff.

S3. SAFETY NOTE CONTENT NOT PARSED
  The app doesn't parse the safety agent's response at all. Whether the agent
  returns JSON, plain text, "CONTINUE", or "ESCALATE:", it all gets dumped
  into the context as a string. The Assistance-agent must interpret it itself,
  with no structured guidance on how to use it.

NAME FIELD HANDLING (inconsistent across reports):
  - [REDACTED], "William", [REDACTED], "[Not provided]", "Not provided"

ROOT CAUSE: The WriteUp-agent instructions contain two unintegrated format

combine them. The model improvises differently each time.

6. MINOR ISSUES
================================================================================

M1. CLEANUP LOCK CONTENTION (app.py:410-414)
  Every request scans all chats under chats_lock. O(n) where n = number of
  sessions. Not an issue for a demo but would bottleneck under load.

M2. REPORT SIZE UNLIMITED
  No size check on WriteUp-agent output. An unusually verbose agent response
  could consume disk space. No practical risk in demo use.

M3. STALE REPORT DRAFT
  If report save fails and the user continues chatting before retrying, the
  cached report_draft won't include the new messages. This is intentional
  (saves Azure quota) but worth knowing.

M4. CALLBACK PENDING EXPIRES SILENTLY
  If a user ignores the callback offer and sends a normal message, line 526
  sets callback_pending=False with no notification. The offer just disappears.

M5. NO OFFLINE FALLBACK
  If Azure agents are unreachable mid-conversation, the app returns a 502.
  No cached responses or degraded mode beyond the explicit --preview flag.
